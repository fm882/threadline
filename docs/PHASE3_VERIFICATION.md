# Phase 3 verification in progress

`tests/process-recovery.test.ts` uses isolated file-backed PGlite and SQLite checkpoint stores with a synthetic gateway. A hard kill during the first in-flight inference request causes recovery to make a second request and publish one logical answer. This demonstrates application-level idempotency for that crash window; it does **not** imply provider-side exactly-once execution. In a real deployment both provider requests could be billed, even if only one final answer is published. Durable execution attempts are capped at two per run; checkpoint publication does not consume another inference attempt.

A second hard-kill fixture stops after the graph has checkpointed a completed answer but before application publication. Restarting with an unavailable gateway publishes that checkpoint without another inference call. Additional hard-kill fixtures cover admission before execution, interruption during research tool-result continuation, and a crash immediately after publication. Each produces one logical turn and one terminal publication. The research graph currently checkpoints the whole chat node rather than the intermediate tool result: recovery at that boundary repeats the model/search sequence, so extra provider calls and charges remain possible. A cancelled or already completed run rejects stale publication and failure attempts. These checks exercise single-process local PGlite and SQLite only; they do not establish multi-replica recovery.

Cancellation fixtures check repeated cancellation, abort propagation, no late publication, and no model continuation after cancellation during search. Browser tests separately exercise an actual stop and a delayed cancel request where completion wins; the interface reports the corresponding terminal state.
