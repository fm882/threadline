# Phase 10 context budget implementation

The local capability manifest supplies the context ceiling. Each chat invocation reserves the configured 1,024 output tokens and a 2,048-unit safety allowance. The prompt compiler measures serialized UTF-8 payload size, adds message framing, and counts schemas/tool definitions and evidence payloads. This is a conservative tokenizer-independent proxy, not a tokenizer count; no per-model tokenizer has been configured.

When a prompt exceeds its envelope, the compiler removes only the oldest complete user/assistant exchanges. It retains system instructions, historical source context, and the current user request. Research calls recompile both the tool-call request and the continuation containing the tool result; the tool result, assistant tool call, structured-output instructions, and tool schema remain in the measured payload. An oversized required prompt becomes a visible limitation; content is not silently truncated. The application has no smaller-context fallback configured, and it does not issue summary or repair calls.

The same research run signal and outer deadline bound both model invocations and search. The current strategy resolves the whole subject list in one search plan and one structured synthesis response; it does not start independent per-subject model/search jobs. Every subject therefore shares the parent's single deadline, attempt limit, model-call/search counters, and serialized-prompt-byte budget. Validation requires one result or explicit gap per requested subject. Traces record compaction cost, removed exchange count, and history coverage without source text.

`tests/context-budget.test.ts` exercises 1,000 distracting exchanges, preservation of the required subject list and current question, schema overhead, complete tool-call/result retention, and visible overflow. `tests/history-context.test.ts` verifies that an oversized original is not sent to the model and produces a visible limitation. `tests/tracing.test.ts` verifies the redacted budget and coverage decision metadata.

The fallback path is implemented but remains disabled in the checked-in manifest. An optional fallback entry is accepted only when the configured fast alias and exact `BEDROCK_FAST_ROUTE` match, the context ceiling is strictly smaller than the main model, streaming/tool-call/prompted-JSON capabilities are explicitly attested, and both fast streaming and the two-call research contract are recorded as passing. Readiness also requires the gateway to advertise both aliases. When the main call fails with a retryable transport, 408, 429, or 5xx error, the client recompiles the exact messages/tool payload against the fallback envelope before reserving and invoking that route. Failed attempts and both prompt sizes count against the same run budget. Abort, context overflow, and ordinary 4xx/capability errors do not trigger fallback. The accepted fallback is then used for the remainder of that research run.

`tests/capabilities.test.ts` rejects missing or incompatible fallback assumptions; `tests/readiness.test.ts` requires the configured fallback alias to be advertised; and `tests/research-client.test.ts` verifies one route switch, smaller-budget recompilation with current-question retention, shared budget accounting, and no retry for an unsupported request. The route-switch test uses a local mock and does not attest provider compatibility.

The current manifest permits only `chat-main-v1`. The example gateway maps `chat-fast-v1` to Amazon Nova Micro. AWS documents a 128K input context window and client-side tool calling for Nova Micro, while its Bedrock model card lists native structured outputs as unsupported ([Nova specifications](https://docs.aws.amazon.com/nova/latest/userguide/what-is-nova.html), [Nova Micro model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-amazon-nova-micro.html)). This application uses tool calls for search and asks for JSON in the continuation prompt, then validates it locally; it does not send native `response_format`. Those general model specifications do not verify the configured LiteLLM route's end-to-end tool-call and research-JSON behavior. Only fast-route streaming has been live-checked, so no research fallback is currently permitted. The two-call live verifier is prepared; run it after allocating a spend cap before adding a fallback attestation. Model-tokenizer accuracy, retrieval quality under large histories, and measured concurrency remain unestablished; synthetic load evidence is in the Phase 12 report.
